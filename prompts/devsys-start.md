description: Size new work and get the planning artifacts it needs before building
argument-hint: "<what you want done>"
---
Determine whether this is new work with the work-intake-and-slicing skill.

1. Inspect the focused active goal and acceptance criteria (use its public tool when available), active slice and recent evidence before deciding scope for: $ARGUMENTS. Recover missing context first. Once the available evidence establishes that remaining work satisfies the approved scope, continue that work directly; do not repeat scope inspection or planning instead of repairing it. Review/completion-auditor repairs, failed verification, and evidence/report closure required by approved acceptance criteria stay in the existing slice without intake or renewed approval. Checkpoints, resume, compaction and delayed notifications alone are continuation, not new requests or authorization; idle does not establish goal completion. If this is genuinely new work or a planned next slice after the prior slice closes, call `devsys_intake` with the request and continue below. Ask only for a real unresolved scope, replacement, authorization or other user-owned decision; do not automatically authorize unrelated work. If no request or active work can be recovered, ask what the user wants done. Preserve all existing approval and blocker rules.
2. Show the user the size and artifacts. Jev sizes the work; uncertain or unavailable judgments go to configured LLM reasoning first. If still unresolved, inspect evidence, narrow the request or provide an evidence-backed explicit size. Do not ask the user merely because a classifier is uncertain; actual user-owned choices such as replacing active work still require confirmation. If the size is already decided (say, in a goal's or plan's up-front planning), pass it as `size` and nobody is asked to size it. Intake never offers to waive review.
3. Produce the recommended planning artifacts first (brief, decision register, journeys, event model and lens review, as applicable), then the task record. To skip an optional recommended artifact, call `devsys_record_departure` with gate `artifact.skipped:<artifact>` and the reason; do not skip silently. The event model remains recommended. Root `ARCHITECTURE.md` is mandatory regardless of work size: it is the self-contained authority for current architecture and architectural goals, without ADR backlinks, source tables or delegated current requirements. Code must conform to it; intent is not verified implementation or delivery. An artifact departure cannot waive this authority or the architecture/ADR policy.
4. Review happens on the finished slice. Create ADRs only for significant or hard-to-reverse decisions; retain their context, rejected alternatives, consequences and reconsideration conditions as history, not competing current requirements. Do not retry rejected ideas without materially changed context. Every new ADR or premerge edit requires its substantive architecture update in the same commit. Each resulting main/trunk commit adds at most one ADR; other records may change in an addition commit only for linked status-only supersession. Merged records are otherwise immutable, including corrections, deletion and renaming. Squash must preserve the paired updates and replacement records, not combine decisions. Bootstrap one cumulative decision/update pair at a time, with verification, independent semantic review and commit before the next decision. Resolve authoritative history and full pending/resulting delivery units; fail closed on missing inputs. Existing-project adoption is prospective and owner-authorized, preserving merged history and unrelated work without retrospective reconstruction.
5. For `capability` and `product` the phase stays `planning` while you produce the artifacts and the plan. The single point where it changes is the user approving the whole plan: then call `devsys_begin_work` so the review and red-first gates switch on (it does nothing if already implementing).
6. For `fix` and `change` the phase is already `implementing`: write the task record, then work it test-first. Both require the fresh-context review rounds; do not ask the user to skip reviews for a fix.
