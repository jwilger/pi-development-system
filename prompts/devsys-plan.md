---
description: Write the plan file for sized work, one task record per slice, and hand it to a goal
argument-hint: "<slug> [what the plan covers]"
---
Determine whether the current request needs planning with the work-intake-and-slicing skill. First inspect the focused active goal and acceptance criteria (use its public tool when available), active slice and recent evidence; recover missing context before deciding scope. Once the available evidence establishes that remaining work satisfies the approved scope, continue that work directly; do not repeat scope inspection or planning instead of repairing it. Review/completion-auditor findings, failed verification and evidence/report closure required by approved acceptance criteria remain in the existing slice without intake or renewed approval. Idle, checkpoints, resume, compaction and delayed notifications alone do not start or replace work; notifications are evidence, not authorization. Genuinely new work or the next planned slice after closure uses intake; unrelated work is not automatically authorized. Ask only for a real unresolved scope, replacement, authorization or other user-owned decision, never classifier uncertainty or remaining acceptance work. Preserve concrete blocker and approval rules.

Use the numbered planning workflow below only for a newly needed plan or an actual material scope change. For an already-approved goal or slice, carry out the remaining acceptance work instead: do not regenerate its plan, request another plan approval, or create a replacement goal. When scope evidence is missing but available through public tools or session context, recover it first rather than entering the planning workflow.

1. Slug and scope come from: $ARGUMENTS. If the slug is missing, derive one from the active slice and say which you chose.
2. Write `docs/plan/<slug>.md` with these sections: Goal and why; Constraints (what must not change); Increments, each shippable on its own and small enough to release, each with an **Acceptance** list (observable checks that say the increment is done) and a final Release step (commit, push, CI green, publish, update) followed by a STOP for the user; for every task a task record whose header is `## <id> — <title>` and whose sections are written exactly as `**Goal:**`, `**Files:**`, `**Interfaces:**`, `**First failing test:**`, `**Steps:**`, `**Run:**`, `**Expected:**`, `**Out of scope:**` (label and colon inside the bold, one section per label); a Progress checklist with one box per increment.
3. Write each task so that someone who sees only that task could finish it. Never write `TBD`.
4. Check handoff task records once with `devsys_task_check`; fix deterministic structural errors together. Subjective flags are advisory: do not rewrite until ready or split by test count. Use repository context unless a concrete missing decision prevents safe implementation; then ask one precise question. After two process-only attempts without implementation or acceptance evidence, simplify to one usable increment and its next behavioral test, or escalate that blocker.
5. For a newly proposed plan or material scope change, stop and ask the user to review before implementation; existing approval covers routine continuation and acceptance repairs. Do not start a goal yet: a goal tool may continue on its own and begin implementing before the review.
6. Only after the user approves the plan: call `devsys_begin_work` (so the review and red-first gates are on while the increment is built; it does nothing if the work is already implementing). A push of a clean, reviewed tree closes the slice, so each genuinely later increment starts with `devsys_intake`; unfinished acceptance repairs are not later increments and remain continuation. Then, if a `create_goal` tool exists in this session, call it with the objective (name each increment's size in it, so every later `devsys_intake` passes `size` and nobody is asked to size it; every increment, including a `fix`, retains the required review rounds without a waiver prompt) "complete docs/plan/<slug>.md honouring its Constraints and Progress checklist, one increment at a time, stopping after each increment's Release step". Otherwise tell the user the plan path so they can start a goal on it. Do not depend on any goal tool's file format.
