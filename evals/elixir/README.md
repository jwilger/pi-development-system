# Elixir/Phoenix profile effect evidence

These finite opt-in runs exercise an actual isolated Pi SDK model choosing typed
plans from synthetic repository evidence. They do not run Mix, ExUnit, property,
LiveView, browser or repository shell commands. Ordinary tests use scripted SDK
responses and never require provider credentials.

## What is assessed

The typed plan selects tagged-tuple errors, pure business logic, appropriate test
levels, exact repository-owned verification commands, no unsolicited dependencies
and the explicit `NOT EXECUTED` evidence marker. The child receives only synthetic
read/submit tools; attempted outside-world effects fail the assessment. This tests
observable tool decisions rather than matching committed skill text.

Cases are a Mix domain change, a Phoenix UI change and a harmless pure-library
control. Fixtures own expected commands and test scope; the profile does not impose
a universal application layout, library or CI command.

## Retained results

- Six original cells: baseline/skill for all three cases, once each. Four passed.
  Skill Phoenix/control failed because the model truthfully began its evidence with
  `NOT EXECUTED` but added explanatory text instead of the exact required literal.
  Both failed records remain unchanged.
- The tool schema was then tightened from arbitrary string to the literal
  `NOT EXECUTED`, preceded by an offline boundary-rejection regression. The scoring
  criterion, skill and prompts were not relaxed or tuned to those outputs.
- Exactly two authorized changed-protocol skill runs, Phoenix/control, each passed
  once. No additional reruns occurred. Historical successful cells were **not**
  reverified under the new protocol and are not presented as new-protocol results.

All eight byte-preserved records and `evidence/manifest.json` retain effective
`openai/gpt-6.1-sol` / `medium`, hashes, transcript, failures and old/new protocol
provenance. CLI refactoring changed its hash between batches; original hashes remain
in the original records. See [the implementation record](../../docs/plan/elixir-profile.md)
for exact commands and integrity checks. Baselines passing do not establish causal
improvement from the skill. These few model runs are limited behavioral evidence,
not proof of general obedience or actual application verification.

## Explicit opt-in execution

Inspect the fixture before choosing a run. For example, with that model available
and a new output path:

```sh
node --experimental-transform-types --no-warnings scripts/eval-elixir.ts \
  --fixture mix --condition skill --provider openai --model gpt-6.1-sol \
  --output /tmp/NEW-elixir-evidence.json
```

Use a new output path and an explicitly selected or repository-configured available
model. Never overwrite prior failures, reroll unchanged inputs to obtain green or
mistake a typed plan for executed verification. New evidence must identify the
current fixture, skill, runner and effective model configuration.
