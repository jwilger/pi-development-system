# Architecture

## Authority and evidence

This document is the self-contained authority for the project's current architecture and architectural goals. New and modified code must conform to it. Requirements below do not depend on another document for their meaning. Statements labelled **implemented** describe code present in the working implementation; they are not claims of release or delivery. Statements labelled **goal** describe required intent not yet established by verification. Test evidence establishes only the behavior actually exercised.

## Purpose and boundaries

The project is an ESM TypeScript extension for the pi coding-agent harness. It provides development planning, session guidance, independent review, model routing, controlled Git workflow and delivery assessment. It is distributed as a pi package containing an extension entry point, skills and prompts. Consumers retain ownership of repository workflow, delivery policy and authorization of irreversible actions.

The extension is not an operating-system sandbox. It must not claim to control external terminals, arbitrary helper programs or extension-internal process execution that does not traverse pi tool-call hooks. A tool refusal, a detected concern and an instruction to the model are different controls and must be reported separately.

## Module responsibilities

**Implemented:** `extensions/development-system.ts` is the composition root. It connects the pi API to configuration, session persistence, planning tools, review, command guards, model judgments, trackers and subagents. Avoid independent copies of application state or hidden alternate composition roots.

- `src/core` contains deterministic decisions and domain transformations. Keep business rules independent of filesystem, process, network and pi lifecycle I/O.
- `src/state` handles repository configuration and persisted session evidence. Parse external configuration at the boundary; do not silently accept unknown or malformed policy inputs.
- `src/context` constructs model-facing instructions and request context. Stable policy and moving workflow state are separate sections.
- `src/planning` implements intake, planning artifacts and decision creation.
- `src/gates` adapts tool-call observations to pre-execution refusals, approvals and evidence recording. Command recognition is not a general-purpose execution sandbox.
- `src/review` coordinates independent review and binds recorded results to the reviewed inputs. A changed input must not inherit unrelated clean evidence.
- `src/jev` owns typed model judgments and their fixtures. Model confidence does not override non-negotiable policy.
- `src/subagents` prepares and runs delegated work. Independent children must receive mandatory policy even without inherited conversation context.
- `src/tracker` integrates work-item lifecycle and delivery evidence. Local slice completion is not proof of whole-issue or remote delivery completion.

**Implemented:** classification first uses a typed judgment. Uncertain, invalid or unavailable judgments enter a bounded, tool-free LLM reasoning cascade using configured model routing and registry credentials. The assessor receives bounded, redacted questions and evidence; validated unresolved results return actionable typed errors rather than silently transferring classifier uncertainty to the owner. Cancellation and usage-accounting failures are not reasons to reroute. Owner approval remains a separate control for actual authorization decisions. Models and providers are not hard-coded.

Expected failures are typed values with stable identifiers. Keep I/O in thin adapters and make deterministic rules testable through observable public behavior. Preserve strict TypeScript and lint checks; do not weaken verification to obtain a pass.

## Event-model validation boundary

**Implemented:** planning uses schema-v1 event-model slices, stored as YAML or JSON, with commands, events, views and Given/When/Then scenarios. Validation reports malformed slices, invalid references and incomplete flows; optional Markdown swimlanes or Mermaid diagrams are derived views, not separate editable requirements. Validation and rendering do not repair or rewrite model files.

Select one validator through the provider handshake at session start, after all extension tools are known and repository configuration is available. The built-in `devsys_event_model_check` is registered only when `event_model.provider` is `builtin` and no extension supplies `event_model_validate`. An external provider replaces, rather than supplements, the built-in validator. If a configured external provider is missing, report the missing integration instead of silently installing or substituting a validator. This preserves a single validation authority and a stable public tool boundary.

## Session and delegation context

**Implemented:** session start and session-tree restoration rebuild persisted development state. Before-agent preparation supplies stable principles and moving state through pi named prompt sections. Request-local context preparation revalidates repository workflow, including automatic tool continuations.

**Implemented in the working changes:** shared architecture policy is included in principles and independent reviewer tasks. Request-local preparation supplies that policy to independent and restored child requests when it is not already present. Forced full-prompt overrides are rejected rather than silently dropping mandatory policy. Missing required system context fails preparation.

**Implemented and exercised:** mandatory policy reaches fresh root requests, automatic continuations, fresh independent children and restored children. Actual manual pi compaction may discard policy from conversation summaries; request preparation supplies it again independently of that summary. Full-prompt overrides are refused even without configured repository workflow. Do not infer coverage of an unsupported delegation mechanism from these fixtures.

## Architecture and decision lifecycle

The root architecture document contains current requirements and goals, including enough information to develop and review without reconstructing a specification from decision history. It must not include decision backlinks, source tables or instructions requiring routine readers to consult historical records. Keep intent distinguishable from verified implementation and delivery.

Decision records preserve context, the decision, alternatives considered and rejected with reasons, consequences and conditions for reconsideration. Consult them for rationale or when reconsidering an approach, not as another source of current requirements. Do not retry a rejected idea without a material change in context. Routine implementation choices do not need a record; architecturally significant or hard-to-reverse choices do.

Each new decision requires a corresponding substantive update here in the same commit. A commit may add only one new decision record. Other decision records may change in that commit only to mark them superseded by the newly added decision. Premerge edits also require corresponding substantive architecture updates in the same commit. File presence, whitespace changes and cosmetic edits are not sufficient evidence of correspondence.

Once merged into authoritative main/trunk, a record must not otherwise change: no corrections, deletion or renaming. Correct or replace it with a new decision and paired architecture update, preserving the original except for its superseded status linked to the new decision. Preserve historical identities; reintroduction cannot bypass immutability. Unsupported historical formats are not permission for automated rewriting.

The policy applies to the resulting commits on main/trunk. Squash delivery must not combine multiple new records, discard paired updates or remove replacement decisions. Use separate delivery units when required. Bootstrap sequentially: one decision, cumulative self-contained architecture containing only decisions introduced so far, verification, independent review and commit before starting the next. Do not manufacture incremental history from a prewritten collection.

## Verification and enforcement boundaries

**Implemented before these changes:** Git guards inspect supported bash tool calls for destructive actions, commit quality, review evidence, test changes and delivery policy. Hard stops require owner authorization; soft defaults require recorded departures. Independent review uses explicit sources, findings, verdict and input evidence. None of these mechanisms alone proves the architecture/history contract.

**Implemented in the working changes:** the decision-creation tool runs sequentially, refuses a second uncommitted numbered record, refuses unavailable HEAD history, rejects symlinked creation directories/templates and creates files without overwriting existing paths. This is creation-path protection, not complete authoritative-trunk, commit or squash enforcement.

**Implemented in the working changes:** a pure structural checker compares exact decision contents and architecture snapshots. It detects multiple additions, missing or word-equivalent paired updates, changes to already-merged records other than exact linked status-only supersession, and reuse of historical paths or numbered identities. Paired premerge edits remain permissible; they cannot be bundled with a different new decision. Untouched historical records need no format conversion. The checker also rejects missing current architecture and recognized inline decision backlinks. Its history sets are inputs that a trusted Git adapter must establish, not assertions a caller may supply to bypass history checks. Word differences are only candidate substantive changes; unfamiliar link syntax and semantic authority still require independent review. A delivery comparison checks both pending and intended resulting snapshot sequences, rejects combined additions in a squash, and requires exact preservation of final architecture and decision contents so replacement records cannot disappear. The Git adapter must prove that those sequences cover every pending commit and the actual proposed delivery. Replacement records cannot disappear in later pending commits either. Prospective checks preserve untouched historical records, including supersession references whose targets were already unavailable at adoption, without demanding retrospective reconstruction.

**Implemented in the working changes:** the Git inspection adapter requires explicit authoritative trunk and full adoption commit identities. It refuses shallow or unresolved ancestry, inspects every linear pending commit and audits post-adoption trunk changes rather than silently grandfathering later violations. Staged inspection reads the actual index tree. Proposed resulting commits must supply their complete parent chain and preserve the full source tree. Git replacements are disabled; policy blobs must be safely represented regular UTF-8 files within inspection bounds. Unsupported history shapes fail closed without rewriting records. Local graft metadata or a graft-file environment override causes a fail-closed refusal without changing that metadata. Recorded nonempty adoption settings in inspected commits cannot silently be replaced by different supplied settings. The adapter rechecks authoritative trunk, HEAD and the staged index before returning an admissible binding, refusing changes observed during inspection. These checks do not lock Git against another process, detect a ref moved away and back between observations, or eliminate the interval between final inspection and actual process execution. Local Git refs and configuration remain owner-controlled trust inputs, not remotely authenticated truth.

**Implemented in the production composition root:** the architecture guard inspects supported literal-message staged commits before bash execution. Structural violations and missing, stale or insufficient exact-bound independent semantic review cause refusal. Compound staging/commit calls, implicit staging and alternate commit makers are refused rather than inspected against an inaccurate tree. A structurally paired change alone cannot run. Actual pi session fixtures exercise production registration and inherited independent review admission, unrelated-child refusal and stale-tree refusal; these are working-code observations, not release claims.

**Implemented in the working changes:** delivery admission accepts only one explicit push of HEAD to the configured remote and trunk, with complete history inspection and independently reviewed delivery-bound evidence. It refuses other recognized push shapes rather than certifying uninspected sources or implicit settings. Recognized literal remote PR-merge commands are refused because their resulting immutable history is not available before execution. Proposed immutable squash histories can be inspected and reviewed explicitly; they do not authorize an opaque remote merge. External hosting APIs and unrecognized wrapper commands remain outside this control, not silently certified delivery paths.

**Goal:** supported workflow and delivery boundaries must reject mechanically decidable violations, including absent or empty paired updates, multiple additions, forbidden merged-record edits/deletion/renaming/reintroduction, invalid supersession, unpaired premerge edits and invalid squash results. Checks that normalize cosmetic differences are only detection aids; independent semantic review remains required for substantive correspondence.

**Implemented in the working changes:** inherited child tool execution carries host-owned root identity, thread path, session file and a unique runtime attempt identity through the root execution bridge. Asynchronous execution-local storage keeps concurrent child identities separate; calls outside a child execution scope have no child identity. Restoring a child preserves its owned session and path but starts a fresh runtime attempt. These facts are not model tool arguments. The host issues a single-use expected reviewer dispatch, and only the corresponding fresh independent reviewer may associate semantic evidence with it. Provenance is not an operating-system security boundary.

**Implemented:** each selected review lens runs in its own fresh independent reviewer with only that lens assigned. Every selected result is required before recording a round. The host designates one of those dispatches to inspect the complete architecture source/result units; other lens results cannot manufacture architecture credit. Architecture review is an additional mandatory concern even when ordinary lens selection would omit it.

**Implemented in the working changes:** existing persisted review rounds carry architecture-specific semantic evidence bound to explicit adoption, authoritative trunk, HEAD, staged tree and the complete ordered source/resulting units. Checks, sources, host-owned origin, refusals and accepted receipts survive restoration; legacy ordinary review remains readable but provides no architecture-semantic credit. The expected independent reviewer attempt and fresh exact bindings are required at commit and delivery. Independent review must explicitly inspect substantive correspondence, self-contained authority, significance, rationale preservation, reconsideration and sequential introduction. Neither concrete citation shape nor an authenticated assertion proves semantic truth. Model-backed evaluations measure instruction effectiveness separately; failed cells must remain visible and require investigation, not weaker expected values or claims of universal compliance.

Verification must include public behavior through real pi sessions, including refusal before prohibited actions execute. Report tested behavior, untested paths and ordinary execution outside extension control separately. Do not claim universal enforcement, delivery or release from isolated helper tests.

## Existing-project adoption and delivery

Adoption is prospective. Upgrade and verify the active extension before introducing new configuration keys: an older already-running extension can reject its next request immediately on encountering unsupported configuration. Do not change live configuration, install an extension or update consuming projects without authorization. Inspect conflicts and propose an explicit history boundary and migration to the owner. Preserve merged records and unrelated work. Do not modify a consuming project, normalize historical records or reconstruct past commit history without authorization.

Delivery must follow repository-owned policy, retain meaningful verification and independent review, and use rationale-bearing Conventional Commits. No history rewriting, verification bypass, unrelated push on a red trunk or unauthorized publication. Push, release and consumer changes require separate authorization. Local working changes and local test results are not evidence of remote delivery.
